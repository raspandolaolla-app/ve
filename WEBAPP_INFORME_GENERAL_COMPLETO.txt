1) FIX DEFINITIVO Y ACTIVACIÓN BLINDADA DE 2FA TOTP (MIGRACIÓN 124 ACTUALIZADA):

     * Prevención de Vulnerabilidad Crítica: Se erradicó cualquier bypass de validación por regex. Se implementó validación criptográfica canónica y estricta en el motor PostgreSQL mediante HMAC-SHA1 y Time-Step RFC 6238.
   - Solución Backend (`supabase/migrations/124_fix_and_enable_2fa_totp.sql`):
     * Limpieza previa exhaustiva con `DROP FUNCTION IF EXISTS` de todas las variantes de RPCs antes de recrearlas.

     * `public.base32_decode(b32 TEXT) RETURNS BYTEA`: Decodificador Base32 puro con casteo explícito `::INTEGER` en `set_byte('\x00'::bytea, 0, ((v_buffer >> v_bits) & 255)::INTEGER)`, erradicando el error `set_byte(bytea, integer, bigint)`.
     * `public.calculate_totp(p_secret_base32 TEXT, p_offset INT DEFAULT 0) RETURNS TEXT`:
       - Cálculo de HMAC-SHA1 con casteo explícito `'sha1'::TEXT` para prevenir `hmac(bytea, bytea, unknown)`.
       - Operaciones de bits con casteo `::INTEGER` en cada segmento para truncamiento dinámico exacto de 6 dígitos.
     * `public.setup_2fa_for_user(p_user_id UUID DEFAULT auth.uid()) RETURNS JSONB`:
       - Genera 20 bytes aleatorios y codifica a Base32 estándar.
       - Construye URI `otpauth://totp/RaspandoLaOlla:...`.
       - Persiste en `public.user_2fa_secrets` con `secret_base32`, `secret`, `is_active = FALSE`.
     * `public.verify_2fa_code(p_user_id UUID DEFAULT auth.uid(), p_code TEXT DEFAULT '') RETURNS JSONB`:
       - Validación criptográfica real: Evalúa intervalos `i IN -1..1` (tolerancia a drift horario de ±30 seg).
       - Soporte para códigos de recuperación de un solo uso (8 caracteres).
       - Generación automática de 8 códigos de emergencia MD5 en la primera activación.
       - Activación atómica en `public.user_2fa_secrets.is_active = TRUE` Y `public.profiles.is_mfa_enabled = TRUE`.
       - Bloqueo por fuerza bruta tras 5 intentos fallidos (10 minutos).
     * `public.get_2fa_status()`, `disable_2fa()`, `enable_2fa()`, `generate_totp_secret()`, `regenerate_recovery_codes()`.
   - Solución Frontend:

   - Problema Corregido: Errores de sintaxis y tipado (`hmac(bytea, bytea, unknown)` y comentarios de línea) al implementar la suite de 2FA en Supabase.
   - Solución Backend (`122_fix_2fa_setup_and_verify_rpcs.sql`):
     * Creación y adecuación de la tabla `public.user_2fa_secrets` con soporte simultáneo para columnas `secret` y `secret_encrypted`.
     * `public.setup_2fa_for_user(user_id UUID) RETURNS JSONB`:
       - Genera 20 bytes aleatorios seguros vía `gen_random_bytes(20)`.
       - Codifica a Base32 con casteo entero estricto `get_byte(...) & 31`.
       - Inserta o actualiza en `user_2fa_secrets` de forma idempotente con `ON CONFLICT (user_id)`.
       - Retorna objeto JSONB con `success: true`, `secret` y `qr_url` listo para apps de autenticación (Google Authenticator, Authy).
     * `public.verify_2fa_code(user_id UUID, code TEXT) RETURNS JSONB`:
       - Decodifica Base32 con casteo explícito en `set_byte('\x00'::bytea, 0, (v_pos::INTEGER))`.
       - Evalúa el contador de tiempo actual y drift temporal (-1, 0, +1 intervalos de 30s) utilizando `v_base_time + i`.
       - Invoca `hmac(..., 'sha1'::text)` con soporte multiesquema (`public` y `extensions`).
       - Al verificar satisfactoriamente, activa el flag `is_active = TRUE`, resetea `failed_attempts` y devuelve `{ success: true, verified: true }`.
     * Aliases de compatibilidad para `generate_totp_secret()` y `enable_2fa(p_code)` para mantener operativos todos los flujos existentes.
     * Permisos asignados a `authenticated` y `service_role` junto con `NOTIFY pgrst, 'reload schema'`.
   - Solución Frontend (`src/services/repositories/TwoFactorRepository.ts`):
     * `TwoFactorRepository.generateTOTPSecret()` invoca prioritariamente `setup_2fa_for_user({ user_id })` con fallback a `generate_totp_secret`.
     * `TwoFactorRepository.enable2FA(code)` invoca prioritariamente `verify_2fa_code({ user_id, code })` con fallback a `enable_2fa`.
     * `TwoFactorRepository.get2FAStatus()` implementa consulta de estado con fallback directo a `user_2fa_secrets`.

     * Actualización de `calculate_totp`: casteo forzado y explícito `'sha1'::TEXT` y bloque resiliente `BEGIN ... EXCEPTION` que busca `hmac` en `public`, en `extensions` o en el `search_path`, garantizando compatibilidad absoluta con cualquier configuración de Supabase.
     * Permisos de ejecución mínimos (`authenticated`, `service_role`) y recarga inmediata de caché vía `NOTIFY pgrst, 'reload schema'`.

1) CORRECCIÓN DEFINITIVA DE CASTING EN 2FA / TOTP (MIGRACIÓN 118):
   - Problema Corregido: Error `function set_byte(bytea, integer, bigint) does not exist` al generar o validar secretos y códigos TOTP 2FA.
   - Causa Raíz: PostgreSQL exige estrictamente que el tercer argumento de la función nativa `set_byte(bytea, integer, integer)` sea de tipo `INTEGER`. En `base32_decode` y funciones afines, la variable acumuladora `v_buffer` es de tipo `BIGINT`, por lo que la expresión `(v_buffer >> v_bits) & 255` conservaba el tipo `BIGINT` en tiempo de ejecución, provocando la falla por no existir sobrecarga con `bigint`.
   - Solución Backend (`118_fix_2fa_totp_bytea_cast.sql`):
     * Función canónica `public.generate_2fa_secret(secret_length INT DEFAULT 20)`: genera bytes con `gen_random_bytes` y utiliza `get_byte(v_bytes, i) & 31` (tipo entero estricto sin conversiones implícitas a `bigint` o `numeric`).
     * Corrección de `public.base32_decode(TEXT)`: casteo explícito `(((v_buffer >> v_bits) & 255)::INTEGER)` en la llamada a `set_byte`.
     * Corrección de `public.calculate_totp(TEXT, TIMESTAMPTZ)`: casteo explícito `::INTEGER` en cada uno de los 8 desplazamientos de bytes de tiempo del contador RFC 6238 (`((v_counter >> ...) & 255)::INTEGER`).
     * Permisos de ejecución mínimos (`authenticated`, `service_role`) y recarga inmediata de esquema mediante `NOTIFY pgrst, 'reload schema'`.

6. SISTEMA MULTIJUGADOR Y PREVENCIÓN DE DUPLICADOS
--------------------------------------------------------------------------------
- Gestión de Salas: Creación de mesas con código de invitación único, selección de costo de entrada, número de jugadores (2 a 4) y visibilidad (pública/privada).
- Sincronización Realtime: `RealtimeManager.ts` escucha cambios en `game_tables` y `game_table_players`, notificando a los componentes de juego en tiempo real sobre asientos, inicios de partida, movimientos y abandonos.
- Regla Estricta de Asientos Únicos:
  1. `uniquePlayers = Array.from(new Map(players.map(p => [(p as any).user_id || p.userId, p])).values())`.
  2. Verificación `players.length !== uniquePlayers.length`.
  3. Si es verdadero: ABORTAR inicio de partida, no crear sesión, no asignar turnos ni bandos y arrojar:
     "Un jugador no puede ocupar dos puestos en la misma mesa".
  4. Los estados de React (`setTablePlayers`, `setCurrentPlayers`) evitan concatenaciones descontroladas de tipo `[...prev, newPlayer]`.
- Presencia y Latido: `PresenceService.ts` mantiene actualizado el estado de conexión de los jugadores en la mesa.
- Herramienta Administrativa de Limpieza: La RPC `admin_cleanup_empty_tables()` y `admin_terminate_game_table()` con bloqueos de concurrencia `FOR UPDATE` para depurar mesas vacías sin afectar la contabilidad.
